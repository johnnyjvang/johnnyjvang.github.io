Project information

  • Category: Mobile Robots / ROS2 Validation
  • Platform: TurtleBot3 Burger
  • Focus: Base motion and odometry validation
  • Project Type: ROS2 Python package

Why I built this package

Before debugging higher-level autonomy systems like Nav2, SLAM, or AMCL, I wanted to verify that the robot’s base motion pipeline was behaving correctly. This package was built to validate the most fundamental mobile robot behaviors: commanded translation, commanded rotation, and odometry-based stopping.

The goal was to remove ambiguity early. If the base does not move correctly, then later failures in localization, mapping, or navigation can be misleading. This project gave me a deterministic way to test the differential drive stack before moving on to more complex robotics problems.

What the package validates

The package directly tests the motion path: 

/cmd_vel → motor controller → wheels → encoders → /odom

It includes six deterministic validation tests:

Test Purpose
timed_forward Move forward for 3 seconds and measure displacement
timed_back Move backward for 3 seconds and measure displacement
odom_forward Move forward until odometry reports 1 foot (0.3048 m)
odom_back Move backward until odometry reports 1 foot
rotate_ccw Rotate counter-clockwise until about 90°
rotate_cw Rotate clockwise until about 90°

What each test tells me

The timed tests answer a simple but important question: If I command a velocity for a fixed amount of time, does the robot travel the expected distance?

The odometry-targeted tests go one step further by checking whether odometry can be trusted as a feedback signal to stop at a target distance. The rotation tests validate angular motion behavior and help catch yaw scaling or encoder-related errors before they affect localization and path following.

Why this matters for the autonomy stack

If the base motion system is wrong, higher-level systems will fail regardless of parameter tuning. This directly impacts:

  • Nav2 path following
  • AMCL localization alignment
  • SLAM map quality
  • costmap behavior
  • collision monitor performance

By validating the base first, I created a clean engineering baseline before moving into sensor validation, TF validation, and localization validation.

Example interpretation

This package helps turn motion debugging into something measurable. For example:

  • ~0.30 m forward in 3 seconds suggests correct encoder scaling
  • ~0.15 m suggests wheel radius or encoder configuration issues
  • ~0.60 m suggests odometry scaling may be doubled
  • straight command but curved motion suggests imbalance or configuration error
  • poor 90° rotation accuracy suggests angular odometry tuning issues

Takeaway

This project reflects how I approach robotics debugging: start with the lowest reliable layer, validate it with repeatable tests, and then build upward into sensors, transforms, localization, and autonomy. Instead of guessing whether a robot “kind of works,” this package measures whether the base behaves the way it should.
