TurtleBot3 Sensors Validation

A ROS 2 (Jazzy) validation suite designed to systematically verify sensor reliability, motion accuracy, and data consistency on TurtleBot3 before using SLAM, Nav2, or autonomy stacks.

Project Overview

This project was built to answer a critical robotics question: "Is the robot actually behaving correctly at the sensor and motion level?"

Rather than debugging SLAM or navigation blindly, I developed a structured validation suite to isolate and verify each subsystem — LiDAR, IMU, and odometry — independently and in combination.

The result is a reusable ROS 2 testing framework that provides measurable confidence in the robot’s sensing and motion pipeline before moving into higher-level autonomy.

What Was Built

  • ROS 2 Python validation nodes for LiDAR, IMU, and odometry
  • Automated test suite runnable via a single launch file
  • Structured output system for test results and summaries
  • Visual validation using plots, logs, and motion-based GIFs
  • Reusable framework for debugging robotic systems

IMU Validation

  • Gyro bias detection
  • Accelerometer noise characterization
  • Yaw drift over time
  • Rotation response validation
  • IMU vs odometry agreement

LiDAR Validation

  • Valid scan range percentage
  • Stationary noise behavior
  • Front obstacle detection accuracy
  • Nearby object stability over time

System Pipeline Understanding

LiDAR → /scan → obstacle detection + validation
IMU   → /imu  → bias, noise, orientation tracking
Odom  → /odom → motion estimation + drift analysis

cmd_vel → robot motion → evaluated by IMU + Odom + LiDAR

Key Engineering Insights

  • Sensor validation must be done before SLAM — otherwise debugging becomes misleading
  • Odometry drift and IMU bias can silently break navigation systems
  • Message timing consistency is critical for synchronization across subsystems
  • Comparing IMU and odometry provides a powerful cross-validation signal
  • Simulation behaves differently than real hardware (noise, slip, latency)

What I Learned

  • How to design structured validation frameworks for robotics systems
  • How to debug distributed ROS 2 systems using topic-level analysis
  • How sensor noise and bias propagate into higher-level failures
  • How to quantify robot performance instead of relying on visual inspection
  • How to build reusable test pipelines for system verification

Why This Matters

Robotics failures are often blamed on SLAM or planning, but the root cause is frequently lower-level sensor or motion inaccuracies.

This project ensures that the robot has a reliable foundation before introducing complex autonomy stacks like Nav2, AMCL, or Cartographer.
